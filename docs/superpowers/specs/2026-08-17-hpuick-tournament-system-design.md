## 1. Goals & priority order

Data integrity → business logic → transaction safety → auditability → ease of operation →
document accuracy → visual polish. Every design decision below defers to that order.

## 2. High-level architecture

```
PWA (static HTML/CSS/JS, installable, manifest + service worker)
  hosted on GitHub Pages (free, public repo — no secrets in frontend code)
        │
        │  fetch() JSON POST, Authorization: Bearer <session token>
        ▼
Google Apps Script Web App  (doPost/doGet single entry point)
  deployed "Execute as: Me (gcbhoranj@gmail.com)", access "Anyone"
        │
        ├── Google Sheet "HPU Inter-College Kabaddi"  — the database (22 tabs, §5)
        └── Google Drive  "HPU Inter College Kabaddi Tournament 2026/"  — documents (§9)
```

Rationale for GitHub Pages over Apps Script HtmlService hosting: HtmlService runs the page
sandboxed inside a `googleusercontent.com` iframe, which unreliably breaks PWA
installability, service-worker caching, and `getUserMedia` camera access needed for QR
scanning on Android/iOS. A separate static host avoids all three at zero recurring cost.

No secrets live in the frontend bundle — only the deployed Web App URL, which enforces its
own auth (§3) on every call regardless of caller.

### Repository layout

```
/backend      Apps Script project (managed with clasp), pushed to the Web App deployment
/frontend     Static PWA (HTML/CSS/JS, manifest.json, service worker), deployed to GitHub Pages
/docs         Specs, implementation plans, dev log
```

### Dev workflow

Local files under git, Apps Script code pushed/pulled with `clasp`. No heavy frontend
framework — a small hand-written JS app (fetch-based API client, simple client-side router,
a handful of screens per role) keeps the installable bundle light, per the "avoid
unnecessary complexity" requirement.

## 3. Authentication

Custom, app-level — **not** Google OAuth for any role. Apps Script executes "as me"
regardless of which human is using the web app, so Sheet/Drive access never depends on the
caller's own Google identity; the app performs its own login layer purely to identify which
committee member is acting, for permissions and audit trail.

- **Admin**: email address + password, both app-level (not a real Google account password).
  First admin account is seeded manually into USERS during setup (password set via a one-time
  setup script, then changeable in-app).
- **Registration / Mess / Accommodation**: short Login ID (`REG1`, `MESS1`, `ACC1`, ...) +
  password, both generated by Admin when creating the user (§9 of original prompt).
- Passwords stored **salted + hashed** using `Utilities.computeDigest` (SHA-256 + per-user
  random salt) — never plaintext, never logged.
- Successful login issues a signed, short-lived session token (HMAC-SHA256 over
  `userId|role|issuedAt|expiresAt` with a server-side secret stored in Script Properties, not
  the Sheet). The PWA stores it (e.g. `localStorage`) and sends it as a Bearer header on every
  call. Token refresh endpoint extends a session while the user stays active.
- Every backend handler resolves the token to `{userId, role}` **before** doing anything else,
  and re-checks the role is authorized for the requested action — the frontend hiding a button
  is a UX nicety only, never the enforcement point.
- Failed logins, disabled-user login attempts, and expired-token calls are logged (not to
  AUDIT_LOG, which is for authenticated actions, but to a lightweight `LOGIN_LOG` for
  security review by Admin).

## 4. ID & numbering design

Two distinct identifier families:

- **Internal record IDs** — never shown on documents, never reused, human-traceable prefix +
  zero-padded sequence: `TEAM-0001`, `INC-0001`, `PKG-0001`, `CPN-0001`, `PAY-0001`,
  `USG-0000001`, `ROOM-0001`, `NOC-0001`, `REF-0001`, `SREF-0001`, `RCT-0001`, `REL-0001`,
  `DOC-0001`, `EML-0001`, `AUD-0000001`, `USR-0001`. Allocated from a `COUNTERS` sub-block in
  SETTINGS, incremented under `LockService.getScriptLock()` so concurrent requests can't
  collide.
- **Document numbers** — the human-facing numbers that appear on receipts, relieving orders,
  registration confirmations, refund vouchers. Each has its own Admin-configurable
  `{prefix, nextNumber, padding}` in SETTINGS (§16 below), allocated under the same lock,
  and **burned, not reused** even if PDF generation fails after the number is issued — a
  failed attempt gets a fresh number on retry rather than risking a duplicate on a real
  document.

## 6. Apps Script API design

Single Web App entry point, `doPost(e)` routing by an `action` string to small per-action
handlers grouped by module (`auth.*`, `admin.*`, `registration.*`, `mess.*`,
`accommodation.*`, `reports.*`). Every state-changing handler:

1. Resolves the Bearer token → `{userId, role}`; rejects if missing/expired/invalid.
2. Re-checks the caller's role is permitted for this action (server-side, independent of
   what the UI exposes — §6/§7/§8 restrictions of the original prompt are backend-enforced).
3. Validates the payload shape and business preconditions (e.g. NOC granted before security
   refund, entitlement remaining before meal consumption).
4. Takes `LockService.getScriptLock()` for anything touching a counter or an entitlement
   balance, so concurrent scans/purchases can't race (§47).
5. Writes the transaction row(s) as new rows (never in-place edits on transactional tabs).
6. Appends an AUDIT_LOG row.
7. Returns `{ok: true, data: ...}` or `{ok: false, error: {code, message}}` — the frontend
   never surfaces raw exceptions to committee users (§91); technical detail goes to Apps
   Script's own execution log for Admin/developer review only.

Idempotency: every mutating request carries a client-generated `requestId` (UUID); the
backend keeps a short rolling window of recently-processed request IDs per action and
rejects an exact repeat, protecting against double-click/retry duplication (§48).

Read endpoints (listing teams, rooms, reports) skip the lock but still enforce role-based
field visibility (e.g. Mess never receives payment amounts in a response payload, not just
hidden in the UI).

## 8. Document generation (PDFs)

**Google Slides as the template engine.** One Slides template per document type (temporary
receipt, final receipt, digital coupon, printed-coupon A4 sheet, relieving order), each with
placeholder tokens (`{{COLLEGE_NAME}}`, `{{GRAND_TOTAL_WORDS}}`, ...) and placeholder images
for signatures/seal/QR. Slides supports exact custom page dimensions in inches, so A5
(5.83"×8.27"), A4 (8.27"×11.69"), and the 3"×2" printed coupons all render at their true
physical size — critical for §84/§35 ("100%/Actual Size" printing must measure correctly).

Generation flow: duplicate the template file in Drive → `Slides.Presentations.batchUpdate`
with `replaceAllText` for text fields → replace placeholder images with signature/seal/QR
image blobs → export the Slides file as PDF via the Drive export endpoint → save into the
correct Drive subfolder (§9) → store the resulting `DriveFileId` on the originating DB row
and in DOCUMENTS.

This satisfies the "template-driven, not hard-coded" requirement of §83: when the real
receipt/relieving-order formats are supplied, the Slides template is edited visually — no
code changes needed for layout/wording changes, only for new dynamic fields.

The A4 printed-coupon sheet is a grid template with cut guides; the generator computes how
many A4 pages are needed for N eligible persons and duplicates the grid slide accordingly,
leaving blank space on the final page rather than stretching coupons to fill it (§36).

## 10. QR architecture

- Token: server-generated, opaque, unguessable (random UUID/nanoid-style string), created
  once per FOOD_COUPONS row at package-purchase time, permanently tied to that Coupon/Package.
- Rendering: a small vendored open-source pure-JS QR-matrix encoder runs inside Apps Script
  (no external network call) to produce the QR image blob used in Slides templates and in the
  PWA's own on-screen digital-coupon view — this keeps QR generation fully self-contained, so
  it can't fail because a third-party service is down mid-tournament.
- Resolution: every scan sends only the token; the backend resolves
  `token → coupon → package → team → entitlements` server-side (§44) and re-runs the full
  10-point validity check (§27/§45) — a screenshot or photocopy of a QR carries no additional
  entitlement, because the entitlement lives in MEAL_ENTITLEMENTS/MEAL_USAGE, not in the QR.

## 11. Email & Share

- `GmailApp.sendEmail` from `gcbhoranj@gmail.com`, PDF(s) as attachments, every send (success
  or failure) logged to EMAIL_LOG with the triggering user (§70).
- Free Gmail quota (~100/day) is expected to comfortably cover this tournament's scale;
  Admin's reports (§75) should surface daily send count so this is visible if it ever becomes
  a constraint.
- "Share" buttons invoke the browser's native `navigator.share()` where supported, falling
  back to a plain download link when unsupported (desktop Chrome, older browsers) — never
  claims automatic WhatsApp delivery (§71/§102).
- On email failure the generated PDF remains available for manual download/share — a failed
  send never blocks the underlying workflow (payment, refund, relieving) from completing.

## 12. Phase decomposition & build order

Matches the original prompt's §106 exactly. Each phase gets its own implementation plan
(via the writing-plans skill) and is built + tested before the next starts:

1. **Foundation** — repo scaffold, Sheet schema creation, Drive folder creation, SETTINGS
   seed, Apps Script project skeleton, PWA shell (manifest, service worker, API client).
2. **Users & roles** — auth (login/session), Admin user management, role-gated routing,
   access-restriction tests.
3. **Registration** — team + multi-incharge registration, rate config/locking, charge
   calculation, payment recording, temporary receipt.
4. **Food packages & coupons** — mandatory Package 1, rolling Package 2/3 logic, coupon+QR
   generation, digital coupon, printed 3"×2" coupons + A4 sheet, email/share, resend/reprint.
5. **Mess** — QR scanner, full validity check, group entry, excess-claim prevention,
   concurrency protection, meal order status.
6. **Accommodation** — room master, allocation/reallocation, occupancy, vacating, NOC.
7. **Refunds** — meal refund calculation (dinner-ordered logic), food refund, security
   refund gated on NOC.
8. **Final documents** — final receipt, relieving order, numbering, signatures/seal, email.
9. **Reports** — Admin dashboard, financial/food/accommodation/departure reports,
   college-wise final statement.
10. **Final QA** — full business-rule test pass per the original prompt's §93–§104.
