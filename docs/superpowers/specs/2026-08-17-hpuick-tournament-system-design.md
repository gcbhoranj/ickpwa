This document is the architecture spec for the full system. Implementation proceeds in

## 1. Goals & priority order

Data integrity → business logic → transaction safety → auditability → ease of operation →
document accuracy → visual polish. Every design decision below defers to that order.

**Scope discipline:** this is a purpose-built utility for one tournament, not a general
SaaS product. Every design choice below is evaluated against "does this help Registration
register a team in minutes, Mess validate a meal in seconds, Accommodation allocate a room
quickly, and Registration settle a departing team accurately" — not against what a
commercial multi-tenant platform would need. Explicitly out of scope: match
fixtures/scoring/live-scores, player statistics, push notifications, SMS, WhatsApp Business
API, billing/subscriptions, multi-tenancy, complex analytics, offline write queuing,
microservices, enterprise IAM.

**Operational capacity target:** 15 simultaneous operational users — REG1–REG5,
MESS1–MESS5, ACC1–ACC5 — plus 1–2 Admin accounts, all working against the same live
database concurrently. Every design below (locking, sessions, audit) is sized for this,
not for enterprise scale.

## 2. High-level architecture

```
PWA (static HTML/CSS/JS, installable, manifest + service worker)
  hosted on GitHub Pages (free, public repo — no secrets in frontend code)
        │
        │  fetch() POST, Content-Type: text/plain, sessionId carried in the JSON body
        │  (see §16 — Apps Script can't read headers or handle CORS preflight)
        ▼
Google Apps Script Web App  (doPost/doGet single entry point)
  deployed "Execute as: Me (gcbhoranj@gmail.com)", access "Anyone"
        │
        ├── Google Sheet "HPU Inter-College Kabaddi"  — the database (22 tabs, §5)
        └── Google Drive  "HPU Inter College Kabaddi Tournament 2026/"  — documents (§9)
```

Rationale for GitHub Pages over Apps Script HtmlService hosting: HtmlService runs the page
sandboxed inside a `googleusercontent.com` iframe, which unreliably breaks PWA
installability, service-worker caching, and `getUserMedia` camera access needed for QR
scanning on Android/iOS. A separate static host avoids all three at zero recurring cost.

No secrets live in the frontend bundle — only the deployed Web App URL, which enforces its
own auth (§3) on every call regardless of caller.

### Repository layout

```
/backend      Apps Script project (managed with clasp), pushed to the Web App deployment
/frontend     Static PWA (HTML/CSS/JS, manifest.json, service worker), deployed to GitHub Pages
/docs         Specs, implementation plans, dev log
```

Local files under git, Apps Script code pushed/pulled with `clasp`. No heavy frontend

a handful of screens per role) keeps the installable bundle light, per the "avoid

## 3. Authentication

Custom, app-level — **not** Google OAuth for any role. Apps Script executes "as me"
regardless of which human is using the web app, so Sheet/Drive access never depends on the
caller's own Google identity; the app performs its own login layer purely to identify which
committee member is acting, for permissions and audit trail.

- **Admin**: email address + password, both app-level (not a real Google account password).
  First admin account is seeded manually into USERS during setup (password set via a one-time
  setup script, then changeable in-app).
- **Registration / Mess / Accommodation**: short Login ID (`REG1`, `MESS1`, `ACC1`, ...) +
  password, both generated by Admin when creating the user (§9 of original prompt).
- Passwords stored **salted + hashed** using `Utilities.computeDigest` (SHA-256 + per-user
  random salt) — never plaintext, never logged.
- Sessions are **server-side records, not self-encoded tokens** (simpler than JWT/HMAC and
  gives Admin real revocation, per recommendation §23): on login the backend creates a
  `SESSIONS` row (§5) with a random opaque `SessionId` (the value the client holds — nothing
  to decode, nothing to forge without guessing a random string), `UserId`, `Role`, `IssuedAt`,
  `ExpiresAt`, `Status(ACTIVE/REVOKED/EXPIRED)`. No script-wide secret is needed for this, so
  there's nothing sensitive to leak beyond the session records themselves.
- The PWA stores the SessionId (e.g. `localStorage`) and sends it as a field in the JSON body
  of every POST request (`Content-Type: text/plain`, parsed server-side) — never as an
  `Authorization` header. This isn't a style preference: the connectivity POC in §16 found
  that Apps Script Web Apps can't complete a CORS preflight (which a custom header forces)
  *and* that `doPost`/`doGet` can't read incoming headers at all even when a preflight
  succeeds — so body-carried credentials are the only transport that actually works. A
  lightweight refresh call extends `ExpiresAt` while the user stays active.
- Every backend handler looks up the SessionId → `{userId, role}` **before** doing anything
  else, rejecting missing/expired/revoked sessions, and re-checks the role is authorized for
  the requested action — the frontend hiding a button is a UX nicety only, never the
  enforcement point.
- Admin gets a "Sessions" view (active sessions per user, with a Revoke action) — useful if a
  device is lost or a login ID needs to be locked out mid-tournament without disabling the
  whole account.
- Failed logins, disabled-user login attempts, and expired/revoked-session calls are logged
  (not to AUDIT_LOG, which is for authenticated actions, but to a lightweight `LOGIN_LOG` for
  security review by Admin).
- No secrets of any kind (passwords, session data, Google credentials) live in the frontend
  repo or in Google Sheets in plaintext. Because sessions are opaque server-side lookups
  rather than signed tokens, there is no script-wide secret to manage at all — the strongest
  form of recommendation §22 ("don't put secrets in the repo") is satisfied by not needing one.

## 4. ID & numbering design

Two distinct identifier families:

- **Internal record IDs** — never shown on documents, never reused, human-traceable prefix +
  zero-padded sequence: `TEAM-0001`, `INC-0001`, `PKG-0001`, `CPN-0001`, `PAY-0001`,
  `USG-0000001`, `ROOM-0001`, `NOC-0001`, `REF-0001`, `SREF-0001`, `RCT-0001`, `REL-0001`,
  `DOC-0001`, `EML-0001`, `AUD-0000001`, `USR-0001`. Allocated from a `COUNTERS` sub-block in
  SETTINGS, incremented under `LockService.getScriptLock()` so concurrent requests can't
  collide.
- **Document numbers** — the human-facing numbers that appear on receipts, relieving orders,
  registration confirmations, refund vouchers. Each has its own Admin-configurable
  `{prefix, nextNumber, padding}` in SETTINGS (§5), allocated under the same lock,
  and **burned, not reused** even if PDF generation fails after the number is issued — a
  failed attempt gets a fresh number on retry rather than risking a duplicate on a real
  document.

of its own. This keeps financial logic in one place, testable independently of document
layout, and means a future change to the receipt's visual format can never silently change
what number appears on it.

## 6. Apps Script API design

Single Web App entry point, `doPost(e)` routing by an `action` string to small per-action
handlers grouped by module (`auth.*`, `admin.*`, `registration.*`, `mess.*`,
`accommodation.*`, `reports.*`). Every state-changing handler:

1. Resolves the `sessionId` field carried in the request body → `{userId, role}`; rejects if
   missing/expired/revoked (see §16 for why it's body-carried, not a header).
2. Re-checks the caller's role is permitted for this action (server-side, independent of
   what the UI exposes — §6/§7/§8 restrictions of the original prompt are backend-enforced).
3. Validates the payload shape and business preconditions (e.g. NOC granted before security
   refund, entitlement remaining before meal consumption).
4. Takes `LockService.getScriptLock()` for anything touching a counter or a shared balance —
   this is deliberately *not* simplified away (recommendation §4/§21). Locked operations:
   registration/receipt/coupon/refund/relieving/accommodation numbering, meal entitlement
   consumption, room allocation, food refund processing, security refund processing, final
   settlement creation, and the departure-lock check-and-set below. The frontend is never the
   authority on any of these — e.g. if remaining entitlement is 5 and MESS1 requests 3 while
   MESS2 simultaneously requests 4, the lock guarantees only one commits at a time and the
   second sees the updated remaining count and is rejected if it would exceed it (§47 example).
4a. For departure specifically (recommendation §5): starting departure is itself a locked
   check-and-set on `TEAMS.DepartureLockedBy` — if already set by another user, the request is
   rejected with "Departure processing is already in progress by REG1" rather than proceeding.
   The lock is cleared when the departure either finalizes (team → RELIEVED) or is explicitly
   cancelled by the same locking user or by Admin. While locked, food refund, security refund,
   final receipt, and relieving order generation for that team are only reachable through the
   locking user's in-progress departure flow, preventing duplicate settlement (recommendation
   §5's "no duplicate final receipt/relieving order" requirement).
5. Writes the transaction row(s) as new rows (never in-place edits on transactional tabs).
6. Appends an AUDIT_LOG row.
7. Returns `{ok: true, data: ...}` or `{ok: false, error: {code, message}}` — the frontend
   never surfaces raw exceptions to committee users (§91); technical detail goes to Apps
   Script's own execution log for Admin/developer review only.

Idempotency: every mutating request carries a client-generated `requestId` (UUID); the
backend keeps a short rolling window of recently-processed request IDs per action and
rejects an exact repeat, protecting against double-click/retry duplication (§48).

Read endpoints (listing teams, rooms, reports) skip the lock but still enforce role-based
field visibility (e.g. Mess never receives payment amounts in a response payload, not just
hidden in the UI).

## 8. Document generation (PDFs)

**Google Slides as the template engine.** One Slides template per document type (temporary
receipt, final receipt, digital coupon, printed-coupon A4 sheet, relieving order), each with
placeholder tokens (`{{COLLEGE_NAME}}`, `{{GRAND_TOTAL_WORDS}}`, ...) and placeholder images
for signatures/seal/QR. Slides supports exact custom page dimensions in inches, so A5
(5.83"×8.27"), A4 (8.27"×11.69"), and the 3"×2" printed coupons all render at their true
physical size — critical for §84/§35 ("100%/Actual Size" printing must measure correctly).

Generation flow: duplicate the template file in Drive → `Slides.Presentations.batchUpdate`
with `replaceAllText` for text fields → replace placeholder images with signature/seal/QR
image blobs → export the Slides file as PDF via the Drive export endpoint → save into the
correct Drive subfolder (§9) → store the resulting `DriveFileId` on the originating DB row
and in DOCUMENTS.

This satisfies the "template-driven, not hard-coded" requirement of §83: when the real
receipt/relieving-order formats are supplied, the Slides template is edited visually — no
code changes needed for layout/wording changes, only for new dynamic fields.

**The document generator never calculates money** (recommendation §24/§25). For the final
receipt it reads a `FINALIZED` SETTLEMENTS row and drops its numbers into the template
verbatim; for the temporary receipt it reads CHARGES. If a required upstream number doesn't
exist yet (e.g. settlement not finalized), generation fails with a clear error rather than
computing a value itself.

The A4 printed-coupon sheet is a grid template with cut guides; the generator computes how
many A4 pages are needed for N eligible persons and duplicates the grid slide accordingly,
leaving blank space on the final page rather than stretching coupons to fill it (§36).

## 10. QR architecture

- Token: server-generated, opaque, unguessable (random UUID/nanoid-style string), created
  once per FOOD_COUPONS row at package-purchase time, permanently tied to that Coupon/Package.
- Rendering: a small vendored open-source pure-JS QR-matrix encoder runs inside Apps Script
  (no external network call) to produce the QR image blob used in Slides templates and in the
  PWA's own on-screen digital-coupon view — this keeps QR generation fully self-contained, so
  it can't fail because a third-party service is down mid-tournament.
- Resolution: every scan sends only the token; the backend resolves
  `token → coupon → package → team → entitlements` server-side (§44) and re-runs the full
  10-point validity check (§27/§45) — a screenshot or photocopy of a QR carries no additional
  entitlement, because the entitlement lives in MEAL_ENTITLEMENTS/MEAL_USAGE, not in the QR.

## 11. Email & Share

- `GmailApp.sendEmail` from `gcbhoranj@gmail.com`, PDF(s) as attachments, every send (success
  or failure) logged to EMAIL_LOG with the triggering user (§70).
- Free Gmail quota (~100/day) is expected to comfortably cover this tournament's scale;
  Admin's reports (§75) should surface daily send count so this is visible if it ever becomes
  a constraint.
- "Share" buttons invoke the browser's native `navigator.share()` where supported, falling
  back to a plain download link when unsupported (desktop Chrome, older browsers) — never
  claims automatic WhatsApp delivery (§71/§102).
- On email failure the generated PDF remains available for manual download/share — a failed
  send never blocks the underlying workflow (payment, refund, relieving) from completing.

## 14. Core flows

**Registration → temporary receipt:** Team details → add incharge(s) → food entitlement
choice (include incharges Y/N) → charges auto-calculated from current locked rates → payment
recorded → temporary receipt generated → email/share to selected incharge(s).

**Coupon flow (package purchase):** Registration purchases a package → backend creates
FOOD_PACKAGES + FOOD_COUPONS (new QrToken) + 3× MEAL_ENTITLEMENTS + N× PRINTED_COUPONS
(PrintBatchId 1) → digital coupon PDF + A4 printed sheet PDF generated → emailed + available
for share/download/print. **Resend** re-sends the existing digital coupon PDF (no new row).
**Reprint** creates a new PRINTED_COUPONS batch (new PrintBatchId) for the *same* CouponId/
QrToken — never a new package, coupon, or QR (recommendation §11).

**Mess scan (group entry):** Scan QR → resolve token → package/team/current-meal-entitlement
→ show College, Package, Eligible, Already Served, Remaining → operator enters count →
locked check-and-commit → MEAL_USAGE row appended → updated Remaining shown. Any valid
physical/digital representative of the package works for any group size up to Remaining
(recommendation §9); excess requests are rejected with the eligible/served/remaining/
requested numbers shown (§43 of the original prompt).

**Departure/refund flow:** Registration clicks "Process Departure" → departure lock acquired
→ screen shows team, incharges, packages, meal usage, security → Accommodation grants NOC
(separate role, separate screen) → Registration calculates food refund (server computes from
MEAL_ENTITLEMENTS + MEAL_ORDER_STATUS, dinner-ordered rule applied automatically, §50–§52) →
refund processed → security refund processed (blocked until NOC = GRANTED) → SETTLEMENTS row
finalized → final receipt generated from the finalized settlement → relieving order generated
(AN/FN selected, incharge wording pluralized automatically) → "Send Final Documents" emails
both PDFs together → departure lock released → team status → RELIEVED.

## 15. Search & Mess summary (recommendations §26–§27)

Simple substring/prefix search, no separate search index needed at this data scale (a few
dozen teams): Registration/Accommodation search Teams by College Name, Registration Number,
or Team ID; Mess additionally searches by Coupon ID (for a lost/damaged coupon lookup without
rescanning). Mess's "Today's Summary" screen aggregates MEAL_ENTITLEMENTS for the current
date+meal, grouped by team: College | Eligible | Served | Remaining — read-only, for

stays uncluttered.

## 16. Connectivity proof of concept (recommendation §21 — do this before building auth)

**Question to answer empirically, not assume:** can a page on one origin (GitHub Pages, or a
local dev server standing in for it) reliably call an Apps Script Web App via `fetch()`,
including how the browser handles the CORS preflight, before the full session/auth system is
built on top of it?

**Plan:**
1. Deploy a throwaway Apps Script Web App (`doGet`/`doPost` echoing back `{ok:true, method,
   receivedBody}`), access "Anyone", execute as the deploying account — no need to use the
   production gcbhoranj@gmail.com account for this experiment.
2. Serve a minimal static HTML page from a different origin (a local dev server on
   `localhost`, standing in for the eventual GitHub Pages origin) that calls the deployed URL
   with `fetch()`, tried both as a "simple request" (`Content-Type: text/plain`, no custom
   headers, credential in the JSON body) and as a request carrying a custom `Authorization`
   header (which triggers a CORS preflight `OPTIONS`).
3. Observe actual browser behavior (console + network tab): does the simple-request version
   succeed cleanly? Does the custom-header version's preflight succeed, or does it fail
   (Apps Script Web Apps are known to not let you control preflight `OPTIONS` responses)?
4. **Decision rule:** if simple requests (credential carried in the POST body, not a header)
   work reliably, that becomes the transport for SessionId — this needs no new component, just
   a request-shape constraint. Only if that genuinely fails does this spec get revisited to add
   the smallest possible fix (e.g. a tiny proxy) — not introduced pre-emptively.
5. Findings get appended to this document as a dated note; the throwaway script/page are
   discarded (or kept as a scratch file, clearly labeled, not shipped).

This is executed immediately after this spec revision is committed, before Phase 1 begins.

### POC findings (2026-08-17) — executed, results below

A throwaway Apps Script Web App was deployed (`gcbhoranj@gmail.com`, standalone project,
`access: ANYONE_ANONYMOUS`, deployed via `clasp`) and called from a real cross-origin browser
page served on `localhost` (a stand-in for the eventual GitHub Pages origin) — not just curl,
since only a real browser enforces CORS.

**Results:**

1. **GET requests work cleanly.** `Access-Control-Allow-Origin: *` is present on both hops of
   Apps Script's response (the `script.google.com` → `script.googleusercontent.com` redirect
   Apps Script always issues), and the browser fetch succeeded and read the JSON body. PASS.
2. **Simple POST works cleanly** when sent with `Content-Type: text/plain` (a CORS-safelisted
   content type, so no preflight) and the payload — including the session credential — as a
   JSON string in the body, parsed server-side with `JSON.parse(e.postData.contents)`. PASS.
3. **POST with a custom `Authorization` header fails.** This header forces the browser to send
   a CORS preflight `OPTIONS` request first. Apps Script Web Apps have no way to handle
   `doOptions` with proper CORS headers — the preflight itself came back as a raw `500`
   error page (confirmed independently via curl), so the browser blocks the real request
   before it's ever sent. FAIL, as anticipated.

**Bonus finding, independent of CORS:** Apps Script's `doGet`/`doPost` handlers do not expose
incoming HTTP request headers at all (there is no `e.headers` or equivalent) — so even if a
custom header's preflight *did* succeed, the backend would have no way to read it. This is a
second, independent reason the session credential must travel in the request body, not a
header.

**Decision (binding, supersedes the "Bearer header" phrasing in §3):** the PWA sends the
session credential as a field in the JSON body of a `text/plain`-content-typed POST (or as a
URL query parameter for pure reads), never as an `Authorization` header. No proxy, gateway, or
additional component is introduced — the direct PWA → Apps Script architecture from §2 stands
unchanged; only the transport detail for the credential changes. The throwaway script and
local test page were discarded after the test (the disposable Sheet/Script under
`gcbhoranj@gmail.com` may still show in Drive/Apps Script listings — safe to delete manually,
non-blocking).

## 20. Phase 5 amendment — Mess Committee panel: scanning + package sales (decided 2026-08-19)

Fills in the two things §14/§15's "Mess scan (group entry)" flow and screen map left as
section-number references to the original prompt, plus one scope addition decided with the
human partner before writing this phase's plan: **the Mess Committee panel also sells food
packages at the counter**, not just Registration.

**The 10-point scan validity check** (server-side, `mess.recordUsage`, re-run on every scan —
resolving the QR only tells you which coupon; this decides whether the claim is honored):
1. Session valid, caller role = MESS (or ADMIN).
2. QR token resolves to an existing `FOOD_COUPONS` row.
3. Coupon `Status` = ACTIVE.
4. Package `Status` = ACTIVE (not CANCELLED).
5. Team `Status` is not LOST/RELIEVED.
6. Today's date matches the target `MEAL_ENTITLEMENTS` row's date (a coupon's three meals are
   each pinned to one specific date, not a range).
7. Server clock is inside that meal's configured start/end window ± grace minutes (§ Phase 4
   `MealTiming*` settings).
8. The meal implied by the current time (Breakfast/Lunch/Dinner) is the one being claimed —
   a coupon can't be claimed against the wrong meal even if some entitlement row exists.
9. Requested count ≤ `RemainingPersons` (`EligiblePersons − ServedPersons`) — the core
   anti-fraud check driving the group-entry scenario the human described: mess scans, sees
   Remaining, asks the team how many are eating *right now*, and denies entry outright if the
   claimed count exceeds Remaining.
10. Request is not a duplicate of an already-processed `requestId` (idempotent retry safety,
    §47/§48).

Any failure returns a clear rejection reason plus the eligible/served/remaining/requested
numbers (§43 of the original prompt) and writes nothing — no `MEAL_USAGE` row, no separate
"denied attempt" record either (decided with the human: keep the ledger a clean record of
actual consumption only; the on-screen rejection is the mess operator's cue to deny entry).
A successful claim appends one `MEAL_USAGE` row and updates `ServedPersons`/`RemainingPersons`
on the entitlement, inside the same script-lock class as other counter-touching operations
(recommendation §4/§21) so two mess counters scanning the same coupon at once can't both
commit past Remaining.

**`MealOrderStatus` is informational, not a scan gate** (decided with the human): Mess sets a
date+meal to ORDERED/CLOSED via `mess.setMealOrderStatus`, shown on the Current Meal screen,
but `mess.recordUsage` never consults it — scanning is gated purely by the 10 points above.
`MealOrderStatus` exists for the later dinner-ordered-vs-not refund rule (§50–§52, Departure
phase), not built here.

**QR input: camera scan with a manual-entry fallback**, both always available on the Scan
screen. Camera decode uses the browser's native `BarcodeDetector` Shape Detection API
(Chrome/Edge; no vendored library, no network call — the same self-contained principle as
`QrEncoder.gs`'s encoder) when the browser supports it; the manual token field covers
unsupported browsers and a damaged/unscannable QR either way.

**Package sales — Mess gets purchase/resend/reprint parity with Registration.** Decided with
the human mid-phase: the Mess Committee panel is also where meal packages get sold at the
counter, not exclusively Registration. This is a role-permission widening, not new backend
logic:
- §12's role matrix row "Purchase food package, generate/email/share/resend coupons" changes
  from MESS ❌ to **MESS ✅** (Registration keeps ✅ — both roles can do this, not exclusive).
- `FoodPackages.gs`'s `purchasePackage_`/`listPackages_`/`resendCoupon_`/`reprintCoupon_`
  (Main.gs actions `registration.package.*`) add `ROLES.MESS` to their existing
  `requireRole_([ROLES.ADMIN, ROLES.REGISTRATION])` checks — same handlers, same screen
  (`packages.js`), reused unchanged for both roles.
- **Team lookup added to Mess's nav**: `listTeams_`/`getTeamDetail_` (`registration.teams.*`)
  also add `ROLES.MESS`, so Mess gets a Teams search screen leading into a team's Food
  Packages screen — needed because a team buying Package 2+ at the mess counter usually isn't
  presenting an already-scanned coupon.
- **Field visibility on the shared team-detail endpoint** (§6 point 7's existing rule, applied
  here rather than duplicating the handler): when the caller role is MESS, `getTeamDetail_`
  omits `charges`, `payments`, and `receipts` from its response — Mess sees team identity and
  incharges (needed to sell a package) but never Dari/security/total-payable figures or the
  temporary receipt. The frontend's Team Detail rendering skips those sections when absent.
- **Package amount stays visible to Mess on the Packages screen itself** (decided with the
  human): `packages.js`'s purchase form and package list already show only the food-package
  amount (rate × eligible persons), never Dari/security/total — narrowing §6's "Mess never
  receives payment amounts" rule to exclude this one screen, where Mess needs the figure to
  collect the right cash at the counter. Every other read endpoint keeps the existing rule
  unchanged.

**Screen map update (§13):** MESS becomes **Current Meal · Scan · Today's Summary · Teams**
(Teams → Team Detail → Food Packages, reusing Registration's existing screen).

**Today's Summary** (§15, recommendation §27): `mess.todaysSummary` aggregates
`MEAL_ENTITLEMENTS` for the current server date+meal, grouped by team — College | Eligible |
Served | Remaining, read-only, unchanged from the original spec description.

**New backend module `Mess.gs`**, actions registered in `Main.gs` under `mess.*`:
`mess.currentMeal` (today's date, current meal + window status, that meal's order status),
`mess.setMealOrderStatus`, `mess.resolveToken`, `mess.recordUsage`, `mess.todaysSummary`,
`mess.searchByCouponId` (lost/damaged coupon lookup, §15). All follow the standard handler
shape (§6): session/role check, lock where the action touches `ServedPersons`/
`RemainingPersons`/`MEAL_USAGE`/`MEAL_ORDER_STATUS`, validate, write, audit-log.

**New frontend `mess.js`** plus a `renderMessDashboard` landing screen (same pattern as
`renderRegistrationDashboard`/`renderAccommodationDashboard` in `app.js`): Current Meal, Scan,
Today's Summary, Teams. The Teams/Team-Detail/Packages path reuses `registration.js`'s
`renderTeamsList`/`renderTeamDetail` and `packages.js`'s `renderPackagesScreen` unchanged,
called from the Mess dashboard instead of the Registration one.

## 21. Phase 6 amendment — Accommodation: reallocate, vacate, NOC issuance (decided 2026-08-20)

Phase 3.5 (§19) deliberately narrowed Accommodation to allocate-only; this closes the rest of
§17's Phase 6 scope. Two decisions made with the human partner before writing this phase's
plan:

- **Allocation stays per-team/per-incharge**, not per-team-member. `ACCOMMODATION` rows
  continue to represent a block of persons in a room, not one row per student — nothing in
  real use so far has needed individual student-level room tracking, and splitting to that
  grain would be pure speculative complexity (YAGNI). Reallocate/vacate operate on existing
  allocation rows at that same grain.
- **NOC issuance is both the status flip the schema already defines *and* a generated
  certificate PDF** — `ACCOMMODATION_NOC` (§5, specified but never created by `setupSchema`
  until now) gates Phase 7's security refund exactly as designed (`PENDING`→`NOC_GRANTED`),
  and granting it also produces a one-page PDF certificate for the incharge to carry, via the
  same Slides-copy-and-render pattern `Receipts.gs` already uses for the temporary receipt.
  `ACCOMMODATION_NOC` gains one field beyond its original spec: `PdfFileId`.

**Backend (`Accommodation.gs`):**
- `vacateRoom_(actorSession, allocationId)` — role `ACCOMMODATION`. Marks the allocation
  `Status: VACATED`, `VacatedAt: now`; if the room was `FULL`, flips it back to `AVAILABLE`
  (mirrors `allocateRoom_`'s inverse: it flips `AVAILABLE→FULL` when an allocation fills the
  last space, so vacating must be able to undo that). Rejects an already-`VACATED` row
  (`ALREADY_VACATED`).
- `reallocateRoom_(actorSession, allocationId, newRoomId)` — role `ACCOMMODATION`. Internally
  vacates the existing row (via the same logic as `vacateRoom_`) then allocates the same
  `PersonsAllocated`/`TeamId`/`SubjectType` into `newRoomId`, reusing `allocateRoom_`'s
  existing capacity/room-type checks rather than duplicating them — implemented as vacate +
  allocate composed together, not a third parallel code path.
- `listActiveAccommodation_(actorSession, kind)` — role `ADMIN`/`REGISTRATION`/
  `ACCOMMODATION`. Active (`Status: ALLOCATED`) allocations joined with team/room info, so the
  Rooms/Teams screens have something to reallocate/vacate *from* (today's `Accommodation.gs`
  only ever looked at *pending* need, never listed existing allocations back out).

**New backend module `Noc.gs`**, actions registered in `Main.gs` under `accommodation.*`:
- `getNocStatus_(actorSession, teamId)` — current `ACCOMMODATION_NOC` row for a team, or a
  synthetic `PENDING`/no-row-yet state if none exists.
- `issueNoc_(actorSession, teamId)` — role `ACCOMMODATION`. Creates the `ACCOMMODATION_NOC`
  row if absent (or rejects `ALREADY_GRANTED` if one already has `Status: NOC_GRANTED` —
  idempotent-safe, matching every other one-shot document action in this codebase), sets
  `Status: NOC_GRANTED`, generates the certificate PDF (team/college name, date, issuing
  Accommodation user, signature line — same fields-per-line layout technique as
  `_buildReceiptLayout_`, its own `_buildNocLayout_`), stores `PdfFileId`.
- `createNocTemplate_(actorSession, force)` — role `ADMIN`, mirrors
  `createTemporaryReceiptTemplate_` exactly (one-time blank template + manual page-size
  resize step); registered as a new `admin.bootstrap.createNocTemplate` action alongside the
  existing `createReceiptTemplate`.

**Schema:** `ACCOMMODATION_NOC` (`NocId, TeamId, Status, IssuedBy, IssuedAt, Notes,
PdfFileId`) added to `setupSchema`'s tab list — idempotent like every other tab there, safe to
re-run on the live production Sheet.

**Frontend (`accommodation.js`):** Rooms/Teams screens' existing allocation rows gain
Reallocate (pick a new room from the same room-type list already fetched for allocation) and
Vacate buttons. New **NOC** screen (completing the spec's 3-screen Accommodation nav, §13):
search/list teams with their current NOC status, a Grant NOC action, and a link to the
generated PDF once granted.

**Testing:** no new tier needed — per the cost-based rationale that created the `mess`/`pdf1`/
`pdf2` split in the first place (Sheets-only work and real document generation don't scale the
same way), vacate/reallocate/redacted-team-access are cheap Sheets round trips and join `fast`
(alongside the existing `rooms_createAndList`/`accommodation_listPendingAndAllocateRoom`); the
NOC-issuance test does real Slides/Drive PDF generation and joins `pdf2`.
